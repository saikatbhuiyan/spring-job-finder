# 07 — Stereotype Annotations in Spring

## Goal

Understand Spring's **stereotype annotations**: `@Component`, `@Service`, `@Repository`,
`@Controller`, `@RestController`, and also `@Configuration`. Learn how they relate, what
(little) each one adds, which layer each belongs to, and how to create your own.

Builds on [note 04](04-component-scan-and-bean-lifecycle.md) (scanning) and
[note 05](05-backend-layers.md) (layers).

Status: `@Component` and `@Configuration` ✅ applied; the others 🧪 verified in a demo.

---

## 1. What "stereotype" means

A *stereotype* is a label for the **role** a class plays. In Spring, a stereotype
annotation does two things:

1. **Makes the class a bean candidate**: component scanning finds it and creates a bean.
2. **Documents its role**: anyone reading `@Service` knows it holds business logic.

Some of them add a small extra behavior on top (§4).

---

## 2. They are all `@Component` underneath (verified)

Java annotations can themselves be annotated. These are called **meta-annotations**. I printed
what each stereotype is annotated with:

```text
@Component       is annotated with [@Indexed]
@Service         is annotated with [@Component]
@Repository      is annotated with [@Component]
@Controller      is annotated with [@Component]
@Configuration   is annotated with [@Component]
@RestController  is annotated with [@Controller, @ResponseBody]
```

So the family tree is:

```text
                         @Component
        ┌───────────┬────────┴──────┬──────────────┐
    @Service   @Repository    @Controller    @Configuration
                                   │
                            @RestController   (= @Controller + @ResponseBody)
```

**Key insight:** `@ComponentScan` looks for `@Component` *including when it appears as a
meta-annotation*. That's why all of these are picked up. Verified:
`@RestController is a @Component? true`.

Where they come from:

| Annotation | Package | Jar |
|------------|---------|-----|
| `@Component`, `@Service`, `@Repository`, `@Controller` | `org.springframework.stereotype` | `spring-context` ✅ (we have it) |
| `@Configuration` | `org.springframework.context.annotation` | `spring-context` ✅ |
| `@RestController` | `org.springframework.web.bind.annotation` | `spring-web` 🔜 (I downloaded it only to inspect it; it's not in the project) |

## 3. All of them get scanned (verified)

```java
@Component      public static class MyComponent {}
@Service        public static class MyService {}
@Repository     public static class MyRepository {}
@Controller     public static class MyController {}
@Configuration  public static class MyConfig {}
```

With `@ComponentScan("st")`, every one became a bean:

```text
beans.MyComponent   ->  runtime class MyComponent
beans.MyService     ->  runtime class MyService
beans.MyRepository  ->  runtime class MyRepository
beans.MyController  ->  runtime class MyController
beans.MyConfig      ->  runtime class Beans$MyConfig$$SpringCGLIB$$0   ← note this!
```

(The names start with `beans.` only because these test classes are nested inside a class
called `Beans`; see note 03 §9.)

**Look at the runtime classes:**
- `@Service`, `@Repository`, `@Controller` beans are **your plain class**. Spring didn't
  change them in any way.
- The `@Configuration` bean is a **subclass generated by Spring** (`$$SpringCGLIB$$`). That
  subclass intercepts calls between `@Bean` methods so they return the singleton instead of
  creating a new object each time (the "full mode" mentioned in note 02's common mistakes).

## 4. What each one is for

| Annotation | Layer (note 05) | Extra behavior beyond `@Component` | Job Finder example |
|------------|-----------------|-------------------------------------|--------------------|
| `@Component` | Any / generic helpers | None | `SlugGenerator`, `Clock` wrapper |
| `@Service` | Business | **None.** Pure documentation of intent (verified: plain class, no proxy) | `JobService`, `ApplicationService` |
| `@Repository` | Data access | **Exception translation:** with a persistence setup (JPA), database errors become Spring's `DataAccessException` hierarchy (🔜 with JPA) | `JobRepository` |
| `@Controller` | Web | Spring MVC detects its `@RequestMapping`/`@GetMapping` methods as HTTP handlers. Methods return **view names** (HTML pages) by default | Server-rendered pages |
| `@RestController` | Web (REST APIs) | `@Controller` + `@ResponseBody`: return values are written **directly to the response as JSON** | `JobController` (`GET /jobs`) |
| `@Configuration` | Configuration | Holds `@Bean` methods, CGLIB-enhanced for singleton semantics | `ProjectConfig` |

### `@Controller` vs `@RestController` (🔜 with Spring Web)

```java
@Controller
class PageController {
    @GetMapping("/jobs")
    String jobsPage() { return "jobs"; }          // → renders the template "jobs.html"
}

@RestController
class JobController {
    @GetMapping("/api/jobs")
    List<JobResponse> jobs() { return ...; }      // → JSON: [{"title": ...}, ...]
}
```

Job Finder is a **REST API**, so it will use `@RestController`.

### "If `@Service` does nothing, why not use `@Component` everywhere?"

It works technically, but:
1. **Readability**: the annotation tells you the layer at a glance.
2. **Tooling and AOP**: you can target a layer, e.g. "log the timing of every method in
   every `@Service`" with an aspect pointcut like `@within(org.springframework.stereotype.Service)`
   (🔜 AOP).
3. **Future-proofing**: Spring may attach behavior to a stereotype later (as it did for
   `@Repository`).

**Rule:** use the most specific stereotype that fits, and `@Component` only for things that
aren't a controller, service or repository.

## 5. Your own stereotype (verified)

Because scanning follows meta-annotations, you can define your own stereotype by
annotating an annotation with `@Component`:

```java
@Target(ElementType.TYPE)               // may be placed on classes
@Retention(RetentionPolicy.RUNTIME)     // kept at runtime so Spring can see it
@Documented
@Component                              // ← this makes it a stereotype
public @interface UseCase {
    @AliasFor(annotation = Component.class)
    String value() default "";          // lets you write @UseCase("name"), like @Component("name")
}
```

```java
@UseCase            public class ApplyForJob {}
@UseCase("postJob") public class PostJobUseCase {}
```

Verified. Both were scanned, and the custom name worked:

```text
beans.ApplyForJob  ->  runtime class ApplyForJob
postJob            ->  runtime class PostJobUseCase
```

- `@Retention(RUNTIME)` is required. Otherwise the annotation is thrown away after
  compiling and Spring never sees it.
- `@AliasFor` forwards the `value` to `@Component`'s `value`, i.e. the bean name.

Teams use custom stereotypes like `@UseCase` or `@DomainService` to make their architecture
explicit (common in "clean architecture" codebases).

---

## 6. Using stereotypes correctly

- ✅ Put them on **classes** (concrete implementations), not on interfaces. Spring creates
  instances of classes.
- ✅ One stereotype per class.
- ✅ Make sure a `@ComponentScan` covers the package (note 04 §4, the bug we hit).
- ❌ Don't put `@Component` on a class *and* also define a `@Bean` for it (note 04 §4, the
  duplicate bug).
- ❌ Don't use `@Service` on a class that talks to the database. That's `@Repository`.

---

## Common mistakes

| Mistake | Result |
|---------|--------|
| Stereotype class outside the scanned package | Silently not a bean → `NoSuchBeanDefinitionException` |
| `@Controller` for a JSON API | Spring tries to resolve the return value as a view name; use `@RestController` |
| Custom stereotype without `@Retention(RUNTIME)` | Spring can't see it; the class isn't scanned |
| Expecting `@Service` to add transactions or similar | It doesn't; transactions need `@Transactional` (🔜) |
| Stereotype on an interface | No bean is created for an interface |

## Interview questions

**Q: What are stereotype annotations?**
Annotations that mark a class's role and make it a candidate for component scanning:
`@Component`, `@Service`, `@Repository`, `@Controller`, plus `@RestController` and `@Configuration`.

**Q: Difference between `@Component`, `@Service` and `@Repository`?**
All register a bean. `@Service` only documents the business layer. `@Repository` also enables
persistence exception translation.

**Q: `@Controller` vs `@RestController`?**
`@RestController` = `@Controller` + `@ResponseBody`: return values are serialised (e.g. to JSON)
instead of being treated as view names.

**Q: Is `@Configuration` a stereotype?**
It's meta-annotated with `@Component`, so it's scanned like one, but it's also CGLIB-enhanced
so that `@Bean` methods return singletons.

**Q: How does component scanning find `@Service` if it looks for `@Component`?**
It checks meta-annotations: `@Service` is itself annotated with `@Component`.

**Q: How do you create a custom stereotype?**
Define an annotation with `@Retention(RUNTIME)`, `@Target(TYPE)` and `@Component` on it (optionally
`@AliasFor` for the name).
